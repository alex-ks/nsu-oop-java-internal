## Кратко о синхронизации

Потоки исполняются параллельно, но работают с общей памятью - отсюда одновременная работа с общей памятью может привести к неприятным и непредсказуемым спецэффектам (от нарушения алгоритма из-за неопределённого порядка выполнения операций до превращения бинарного представления объекта в кровавое месиво). Чтобы обезопасить себя от этих спецэффектов и сделать поведение программы предсказуемым, придумали средства синхронизации. По большей части эти средства реализуются либо аппаратными инструкциями, либо предоставляются операционной системой - вы не сможете реализовать их самостоятельно.

Нас сейчас интересует конкретный примитив синхронизации - *мьютекс* (от анг. mutual exclusion). Мьютекс - это объект с двумя методами: *захватить* (lock) и *освободить* (unlock). Их смысл в следующем: если один поток *захватил* мьютекс, то любой другой поток, пытающийся захватить мьютекс, будет остановлен операционной системой до тех пор, пока первый поток не *освободит* его. Это позволяет гарантировать безопасность доступа к конкретным данным - к тем, перед использованием которых поток всегда захватывает мьютекс и после использования которых всегда освобождает его.

В Java мьютекс является основой блока `synchronized`:

```Java
synchronized (someObject) {
  // Some code.
}
```

В Java в каждый объект встроен мьютекс. При входе в такой блок поток захватывает мьютекс внутри объекта `someObject` и освобождает этот мьютекс после выхода из блока. Таким образом гарантируется, что операции внутри такого блока всегда выполняются только одним потоком. В этой ситуации бъект `myObject` называется *монитором*. Помимо `synchronized`-блоков в Java есть ещё `synchronized`-методы - по сути, это метод, внутри которого сразу объявлен блок `synchronized (this) {...}`.

На базе мьютекса построен примитив условной переменной. В Java это выглядит так: когда объект захвачен в блоке `synchronized`, то становятся доступны для вызова методы `wait()`, `notify()` и `notifyAll()` у этого объекта (иначе при их вызове выбросится `IllegalMonitorStateException`). При вызове `wait()` поток освобождает монитор и останавливается ОС до тех пор, пока какой-либо другой поток, захвативший этот монитор, не вызовет `notify()` или `notifyAll()`. При вызове `notify()` *один* из потоков, вызвавших `wait()` просыпается, пытается захватить монитор и продолжает исполнение с момента вызова `wait()`. При вызове `notifyAll()` *все* потоки, вызвавшие `wait()` просыпаются и пытаются захватить монитор для продолжения исполнения с момента вызова `wait()`.

С Java 5 появились похожие, но более гибкие классы `Lock` и `Condition`. Так, они позволяют:
- защитить критической секцией цепочку вызовов методов, а не только один блок кода
- попытаться захватить мьютекс без блокирования в случае неудачи
- узнать, какие потоки ждут на мьютексе

И т.д. Но в добавок к большей гибкости они получают следуюшую проблему:

```Java
lock.lock();
throw new Exception();
lock.unlock();  // Will never be called
```

Для `synchronized`-блоков монитор освобождается всегда при выходе из блока, даже при выбросе исключения.

## Threadpool

Создание и завершение потока - дорогое удовольствие (долго и занимает системные ресурсы - количество потоков в OS ограничено). Если операции мелкие, то создание и завершение потока может занимать значительно больше времени, чем исполнение задачи. Для таких ситуаций придумали следующее: заранее создавать ограниченное количество рабочих потоков (worker thread) и научить их брать задачки из общей кучки по мере освобождения. Это и есть threadpool - пул потоков.

Для создания пула потоков нам понадобится:
- Собственно, множество потоков - причём фиксированное их число
- Очередь задач, в которую клиенты эти задачи будут складывать, а рабочие потоки - забирать
  - Эта очередь должна быть синхронизированной, причём как на удаление (если очередь пустая, рабочий поток должен подождать), так и на добавление (если очередь полная, клиент должен подождать)

Параметром пула потоков, очевидно, является количество рабочих потоков. Если этих потоков мало - у нас будет быстро расти очередь задач и (возможно) неэффективно расходоваться ресурсы системы. Если потоков много - они будут биться друг с другом за процессорное время и мы получим просадки производительности из-за частого переключения контекстов. Но об этом вам расскажут на курсе ОС.
